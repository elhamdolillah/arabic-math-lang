# مراجعة الآليات 159–161 وعلاقتها بعقد `بلا_تخصيص`

## الحالة

هذه المراجعة تصنيف دستوري مستقل للمرفق المقدم، وليست تنفيذًا لمصادر COBOL أو C أو Common Lisp. لم تُعدّل Grammar، ولم يُعدّل baseline النواة، ولم تُقبل أي ميزة runtime.

```text
CONSTITUTION_REVIEW=PASS_WITH_GUARDS
SOURCE_EXECUTION=NOT_PERFORMED
RUNTIME_FEATURES_ADMITTED=0
GRAMMAR_MODIFIED=NO
BASELINE_MODIFIED=NO
AUTO_PROMOTION=DENY
```

## النتائج

| الرقم | المفهوم الموحّد | التصنيف | العلاقة بعقد `بلا_تخصيص` |
|---:|---|---|---|
| 159 | إعادة تهيئة حالة البرنامج الفرعي | `RESEARCH` | مجاور، لكنه لا يثبت نقاء الدالة أو غياب التخصيص. |
| 160 | وصول ذاكرة متطاير مقيّد | `ABSTAIN_UNTIL_EVIDENCE` | غير كافٍ؛ لا يثبت الذرية أو ترتيب الذاكرة بين الخيوط. |
| 161 | مستوى سلامة فحص الأنواع والحدود | `ABSTAIN_UNTIL_EVIDENCE` | حاجز سلامة مستقل، ولا يثبت أثر التخصيص. |

الآلية 159 تصلح لاحقًا كعقد مستقل لإعادة ضبط حالة صريحة عند كل استدعاء، بشرط تعريف نطاق الحالة والآثار الجانبية وإعادة الدخول. لا يجوز مساواتها تلقائيًا بـ`ALLOC_NONE`.

أما الآلية 160 فلا يجوز اعتماد ادعائها بوصفه ضمانًا عامًا للحتمية؛ فالعقد المطلوب يجب أن يحدد نموذج الذاكرة، والذرية، ونطاق الترتيب، وواجهة الجهاز أو التزامن. وتحتاج الآلية 161 إلى عقد مستقل لنطاقات الفهرسة وأنواع الأخطاء وحدود التحسين، ولا يجوز افتراض أن مستوى السلامة الخارجي يساوي عقد MAL موحدًا.

## القرار

تبقى الآليات الثلاث خارج التنفيذ العربي في الوقت الحالي. الأولوية التالية هي عدم تخصيص أي آلية runtime، بل صياغة عقد منفصل لإعادة تهيئة الحالة للآلية 159، وعقد نموذج ذاكرة مستقل للآلية 160، وعقد فشل وفحص حدود مستقل للآلية 161. لا يُسمح بالترفيع إلا بعد AST وABI وcorpus موجب وسالب وتنفيذ مزدوج وبصمة سلسلة ناجحة.
