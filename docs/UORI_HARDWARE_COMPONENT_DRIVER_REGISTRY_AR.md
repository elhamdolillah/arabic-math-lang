# سجل مكوّنات العتاد والتعريفات في UORI

## 1. الغرض

يحدد هذا المستند السجل المرجعي الذي يربط مكوّنات اللوحة الأم أو الجهاز بهويتها الوصفية، ومعرّفاتها المعيارية، ومصادر مواصفاتها، وتعريفاتها، ووحدات Bridge المحتملة. السجل لا يعدّ المكوّن مثبتاً لمجرد ظهوره في صورة؛ فالصورة تنشئ مرشحاً، بينما يحتاج الانتقال إلى الحالة المثبتة إلى دليل مستقل قابل لإعادة الإنتاج.

## 2. حقول السجل الموحد

| الحقل | الوظيفة | قاعدة القبول |
|---|---|---|
| `component_id` | معرف ثابت للمكوّن داخل UORI | يولد حتمياً ولا يعاد استخدامه |
| `revision` | إصدار سجل المكوّن | يتغير عند تغير الهوية أو العقد |
| `observed_at` | وقت الرصد | يسجل بتوقيت موحد |
| `image_hash` | بصمة الصورة الأصلية | إلزامية في مسار التعرف البصري |
| `location` | موضع المكوّن على اللوحة | يصف المرجع المكاني ولا يثبت الوظيفة وحده |
| `visual_candidates` | المرشحات المستخرجة من الصورة | موسومة `HYPOTHESIS` |
| `standard_ids` | معرّفات PCI أو USB أو غيرها | لا تقبل إلا من قراءة ناقل أو مصدر موثوق |
| `datasheet_refs` | أوراق البيانات والمواصفات | يجب حفظ الرابط والإصدار والبصمة عند الإمكان |
| `driver_refs` | التعريفات أو واجهات التشغيل | يجب تحديد المصدر والترخيص والتوافق |
| `bridge_candidate` | وحدة Bridge المقترحة | اقتراح غير قابل للتحميل تلقائياً |
| `assembly_contract` | عقد تعليمات Assembly المسموح بها | لا يضم كتابة أو طاقة قبل التفويض |
| `evidence_chain` | سلسلة الأدلة والبصمات | مطلوبة قبل `VERIFIED` |
| `status` | حالة السجل | `HYPOTHESIS`, `MATCHED`, `VERIFIED`, `QUARANTINED`, `ABSTAIN` |

## 3. هرم مصادر الهوية

تبدأ المطابقة من البيانات التي يمكن قراءتها دون إتلاف: معرّفات الناقل، وواصفات USB، ومعلومات Firmware، ووسوم القطعة، ثم تُقارن بالمواصفات الرسمية وملفات التعريف الموقعة. يمكن استعمال رموز فئة USB لتكوين هوية وظيفية أولية، كما يمكن استعمال صيغ معرّفات PCI مثل المورّد والجهاز والمراجعة والفئة، لكن هذه المعرّفات لا تثبت بمفردها أن كل وظائف الجهاز آمنة أو أن تعريفاً معيناً مناسب للتحميل [1] [2] [3].

تحتفظ UORI بسجل مصدر لكل معلومة. فإذا كانت المواصفة متاحة بشروط ترخيص تحد من تدريب الذكاء الاصطناعي أو الاستخدام التجاري، فلا تُنسخ مادتها إلى نموذج أو منتج إلا بعد فحص الترخيص. ويُحفظ الرابط والتاريخ والبصمة، ويُستخدم المصدر للاستدلال الموثق ضمن حدوده [1].

## 4. عقد التعريف

لا يُعد ملفاً تعريفياً صالحاً للإدماج إلا إذا حدد الناقل، ومعرّفات الأجهزة التي يطابقها، وإصدار الواجهة، ونطاق الذاكرة أو المنافذ، وعمليات القراءة والكتابة، ومتطلبات الطاقة، وحالات الفشل، وخطة الإلغاء. ويجب أن يبين التعريف هل يعمل عبر طبقة نظام التشغيل، أو عبر VFIO أو واجهة عزل مماثلة، أو في بيئة UORI مباشرة مصرح بها.

وثائق Linux الرسمية تعرض نموذجاً واسعاً لواجهات تعريفات الأجهزة وواجهات PCI وUSB وI3C وUART وGPIO وSPI وWi‑Fi وVFIO؛ ويستفاد منها كنماذج تكامل، لا كدليل على أن UORI يملك تعريفاً أصلياً لكل هذه الناقلات [3].

## 5. حالات القرار

| الحالة | المعنى | الإجراء |
|---|---|---|
| `HYPOTHESIS` | مرشح بصري أو استدلالي | لا وصول فعلي ولا تحميل |
| `MATCHED` | توافق أولي مع مصدر أو معرف | قراءة آمنة فقط في بيئة مقيدة |
| `VERIFIED` | تقاطع أدلة واختبارات ناجحة ضمن نطاق محدد | يمكن طلب التفويض لوحدة Bridge |
| `QUARANTINED` | خطر أو تعارض أو تعريف غير موثوق | عزل ومنع الانتشار |
| `ABSTAIN` | نقص دليل يمنع الحكم | تسجيل السبب وانتظار دليل جديد |

## 6. قاعدة عدم الخلط بين التعريف والإثبات

وجود تعريف منشور لا يثبت أن العتاد الموجود هو الجهاز الذي يصفه التعريف، ونجاح التعرف على الجهاز لا يثبت سلامة كل عمليات التعريف. لذلك يحتفظ السجل بثلاثة أدلة منفصلة: دليل الهوية، ودليل التوافق البرمجي، ودليل السلامة التشغيلية. لا يكفي أي واحد منها منفرداً للانتقال إلى التحكم المباشر.
