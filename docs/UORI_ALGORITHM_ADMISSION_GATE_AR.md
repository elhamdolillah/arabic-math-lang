# بوابة قبول الخوارزميات في UORI

**الحالة:** `PLANNED_SPECIFICATION` — مواصفة تصميمية لم تُثبت بعد على عينات واسعة أو في بيئة إنتاج.

## 1. الغرض

تمنع البوابة إدخال أي خوارزمية إلى نواة UORI أو إلى شبكة الأنوية قبل تحديد المصدر، والهدف، والموارد المطلوبة، والآثار الممكنة، وشروط الإلغاء. ويجب التمييز بين **الفيروس أو البرمجية الضارة**، و**الخوارزمية غير المفيدة أو خارج نطاق المنتج**، و**الخوارزمية غير المعروفة**؛ فالفئة الثالثة لا تُقبل ولا تُطرد حكماً، بل تُعزل ويُطلب دليل إضافي.

## 2. المسار الإلزامي

| المرحلة | الفعل | الحكم عند نقص الدليل |
|---|---|---|
| التعريف | حساب بصمة المحتوى وتسجيل المصدر والإصدار | `ABSTAIN` |
| التحليل الساكن | فحص الصلاحيات، التبعيات، المسارات، والواجهات | `BLOCKED` عند مؤشرات خطرة غير مفسرة |
| التحليل السلوكي المعزول | تشغيل محدود بلا أسرار أو شبكة أو كتابة خارج مساحة مؤقتة | `ABSTAIN` إذا تعذر العزل |
| مطابقة السياسة | مقارنة السلوك والغرض بعقد UORI | رفض أو امتناع |
| المراجعة | جمع الاختبارات والنتائج والبصمات | `ABSTAIN` إذا كان الدليل ناقصاً |
| التفويض | منح أقل صلاحيات لازمة ومدة محددة | لا تشغيل بلا تفويض |
| المراقبة | قياس الموارد والآثار وقابلية الإيقاف | إيقاف عند تجاوز الحد |

## 3. منع الادعاءات المضللة

لا يجوز للبوابة أن تصف خوارزمية بأنها آمنة أو نافعة أو تعليمية اعتماداً على اسمها أو على اقتراح نموذج توليدي. النموذج التوليدي يمكنه اقتراح فرضية أو شرح نتيجة، لكنه لا يمنح قبولاً ولا يبدل الحكم. كما لا يكفي نجاح التحليل الساكن لإثبات غياب البرمجيات الخبيثة؛ لذلك يبقى الادعاء محدوداً بنطاق الاختبارات والبيئة والعينة.

## 4. سياسة المحتوى

تقبل الخوارزمية إذا كان غرضها محدداً، وسلوكها ضمن العقد، ومصدرها وبصمتها موثقين، واختباراتها قابلة لإعادة التشغيل، وصلاحياتها مقيدة. تُرفض مباشرةً عند وجود حمولة معروفة ضارة أو محاولة تجاوز البوابة أو استخراج أسرار أو توسيع الصلاحيات بلا تفويض. أما الألعاب أو التطبيقات التي لا تحقق هدفاً تعليمياً أو نفعياً مثبتاً فلا تُقبل ضمن **المجموعة الأساسية**؛ ولا يترتب على ذلك حكم شامل على قيمتها البشرية أو منعها من كل نظام آخر.

## 5. عقد القبول

يتضمن عقد القبول: هوية الخوارزمية، بصمة SHA-256، المصدر، الترخيص، الإصدار، الغرض، المدخلات والمخرجات، الصلاحيات، حدود الزمن والذاكرة والتخزين، الشبكات المسموح بها، بيانات الاختبار، معيار النجاح، خطة الإلغاء، ومرجع سجل الأدلة. أي تغيير في المحتوى أو التبعيات الحرجة يلغي العقد ويستوجب فحصاً جديداً.

## 6. الاختبارات الدنيا

| الاختبار | PASS الممكن |
|---|---|
| إعادة حساب البصمة | البصمة مطابقة للسجل |
| تشغيل بلا شبكة | لا محاولة شبكة غير معلنة |
| تشغيل بلا أسرار | لا وصول إلى أسرار البيئة |
| حدود الملفات | لا قراءة أو كتابة خارج المساحة المصرح بها |
| حدود الموارد | لا تجاوز للزمن أو الذاكرة المتعاقد عليها |
| الإيقاف | يتوقف التنفيذ وفق عقد الإلغاء |
| ثبات المخرجات | يتكرر المخرج عندما تكون المدخلات والبيئة ثابتة |
| فحص التبعيات | كل تبعية معروفة ومثبتة البصمة أو موسومة بالامتناع |

## 7. حالات البوابة

الحالات الرسمية هي: `CANDIDATE`، `ISOLATED`، `ANALYZED`، `AUTHORIZED`، `ADMITTED`، `REJECTED`، `ABSTAIN`، و`BLOCKED`. لا تعني `ANALYZED` أو `AUTHORIZED` أن الخوارزمية آمنة على نحو مطلق، ولا تعني `ABSTAIN` أنها ضارة؛ بل تعني أن الدليل غير كافٍ لاتخاذ قرار قبول.

## 8. حدود القاعدة العليا

تعبير «يطرد كل خوارزمية خبيثة» هدف أمني ومعماري، وليس ضماناً مطلقاً. الإثبات الكامل يتطلب تعريفاً تشغيلياً للخبث، ونموذج تهديد، وبيانات اختبار ممثلة، وأدوات تحليل مستقلة، وتجارب قابلة لإعادة الإنتاج. إلى أن تتوفر تلك الشروط، تستخدم UORI صياغة محافظة: **تمنع ما تكشفه الاختبارات من خطر، وتعزل ما لا تستطيع الحكم عليه، وتمتنع عن ادعاء الكشف الكامل**.

## 9. طلب محول اتصال جديد

عندما تكشف النواة واجهة لا تملك لها محولاً معتمداً، تنشئ طلباً يحدد معرف الواجهة، والبروتوكول وإصداره، واتجاه البيانات، ونوع الطرف، والبيئة المستهدفة، والعمليات المطلوبة، وأقل صلاحية لازمة، ومؤشرات الخطر، وشرط الإيقاف، والاختبارات المتوقعة، ومصدر المواصفة، وبصمات الملفات المرشحة. لا يُعد طلباً صالحاً ما لم يحدد الغرض والحدود والنتيجة القابلة للتحقق.

يمر الطلب بالمراحل الآتية: صياغة النطاق، تحديد المصدر، حساب البصمة، الفحص الساكن، التشغيل المعزول، مطابقة العقد، الاختبار على محاكٍ أو هدف محدد، المراجعة، ثم التفويض المحدود. وإذا تعذر إثبات أي مرحلة، تكون النتيجة `ABSTAIN` أو `BLOCKED` بحسب سبب التعذر، ولا يُستبدل النقص بتخمين مولد آلياً.

## 10. مستويات القبول

| المستوى | الدلالة | حدود الاستخدام |
|---|---|---|
| `PROPOSED` | فكرة أو خوارزمية مرشحة | لا تنفيذ مؤثر |
| `SANDBOXED` | تشغيل داخل عزل | اختبار داخلي فقط |
| `VERIFIED_SIMULATION` | اجتياز محاكاة موثقة | لا يثبت عتاداً حقيقياً |
| `VERIFIED_TARGET` | اجتياز على هدف محدد وإصدار معلوم | الهدف المحدد فقط |
| `ADMITTED_LIMITED` | إدراج بصلاحيات ونطاق ومدة | العمليات المتعاقد عليها فقط |
| `REJECTED` | مخالفة أو خطر مثبت | ممنوعة |
| `ABSTAIN` | دليل غير كافٍ | لا قبول |

لا يثبت نجاح محول UART على جهاز واحد نجاحه على كل واجهات UART، ولا يثبت نجاح Bluetooth عبر مكدس النظام وصولاً مباشراً إلى المتحكم، ولا يثبت نجاح socket محلي الثقة بالطرف البعيد. ويرتبط كل قبول بالهدف والإصدار والبيئة وسجل الاختبار الذي أنشأه.

## 11. الدليل

كل قرار يرفق بسجل خام، ورمز خروج، وبصمات المدخلات والمخرجات، ونسخة سياسة البوابة، وبيئة التنفيذ. وتُربط السجلات بسلسلة SHA-256. سلامة السلسلة تثبت عدم تغير السجل بعد إنشائه، ولا تثبت وحدها صحة الاستنتاج الأمني.
