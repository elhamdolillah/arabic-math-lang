# تصميم طبقة Rust وBare-Metal في نواة UORI

**الحالة:** `DESIGN_PROPOSAL` — هذه الوثيقة قرار تصميم قابل للاختبار، وليست دليلاً على تشغيل النواة على عتاد bare-metal.

**الغرض:** تحديد ما يمكن الاستفادة منه من نماذج Rust وواجهات واصفات الملفات وإدارة الذاكرة والحساب العددي، مع منع نقل افتراضات بيئة Unix أو أمثلة المحاكاة إلى النواة بلا دليل.

## 1. الحكم التنفيذي

القرار المعتمد هو فصل UORI إلى نواة منطقية مشتركة، وطبقة تشغيل مستضافة، وطبقة bare-metal خاصة بالهدف. النواة المنطقية تستخدم `core` ومقابض قدرات مجردة، ولا تعرف `std::fs::File` ولا أرقام واصفات Unix. أما `std::fs::File` و`AsFd` و`OwnedFd` فتستعمل في الموائم المستضاف فقط، عندما يكون الهدف نظام تشغيل يوفر ABI وملفات ومقابض فعلية.

ويُعتمد الحساب الصحيح ذي الحدود المعلومة، وخصوصاً fixed-point أو أعداد صحيحة ذات عرض ثابت، في مسار النواة الافتراضي. لا تُدخل العائمة إلى النواة لمجرد سهولة النموذج؛ فإذا تطلب هدف محدد العائمة، يُثبت وجود ABI المناسب أو تُضمّن مكتبة builtins بعد اختبار ربط مستقل. لا يُعد ظهور رموز soft-float أو نجاح الربط وحده برهاناً على صحة الحدود العددية.

## 2. تصنيف المدخلات الواردة

| المدخل | القرار | سبب القرار | موضعه |
|---|---|---|---|
| `AsFd` و`BorrowedFd` | معتمد في المضيف | استعارة مرتبطة بعمر الكائن وتقلل تحويل المقابض إلى أعداد عارية | `hosted/` |
| `AsRawFd` | مسموح عند حدود FFI فقط | يعيد عدداً بلا ضمان عمر؛ لا يُخزن ولا يُمرر بعد انتهاء المصدر | طبقة FFI مضبوطة |
| `IntoRawFd` | مسموح عند نقل الملكية المقصود | يستهلك المصدر ويُلزم الجهة المستقبلة بإدارة الإغلاق | مالك مورد صريح |
| `OwnedFd` | معتمد في المضيف مع تصحيح مهم | هو مالك RAII ويغلق الوصف عند إسقاطه؛ ليس مرادفاً لتسريب المورد | `hosted/` |
| `GlobalAlloc` و`alloc` | معتمد بعد تهيئة MMU ومثبتات التزامن | `no_std` لا يوفر heap تلقائياً | `memory/` |
| Bump allocator | معتمد للتمهيد والذاكرة المؤقتة فقط | لا يدعم تحريراً فردياً؛ إعادة الضبط العامة ليست مناسبة لبيئة تشغيل عامة | `boot/` أو arenas |
| Linked-list allocator | مرشح مرجعي تعليمي | كلفته وتجزئته تحتاج قياساً، ولا يعتمد قبل اختبارات الضغط | تجارب |
| Slab/fixed-size blocks | الخيار المفضل لكائنات النواة المتكررة | سلوك زمني أوضح وتجزئة داخلية مضبوطة | `memory/slab/` |
| مثال allocator الذري الوارد | مرفوض للإنتاج بصورته الحالية | لا يتحقق من كل حالات overflow والتهيئة والتزامن وحدود `dealloc`، وإعادة المؤشر عند عدّاد صفر ليست سياسة عامة آمنة | لا يُدمج |
| `compiler_builtins` | خيار مشروط بالهدف | يعالج رموزاً مفقودة في الربط، لكنه لا يثبت صحة الحساب ولا يناسب كل target | ملف هدف واختبار ربط |
| `#![feature(compiler_builtins_lib)]` | غير معتمد افتراضياً | ميزة غير مستقرة مرتبطة بنسخة/مسار بناء محدد | لا تدخل النواة المستقرة بلا قرار |
| closures و`dyn Fn` | لا تدخل ABI النواة الخام | تمثيلها compiler/ABI-specific ويضيف حالة ومؤشرات غير لازمة | طبقة أدوات فقط |
| نماذج الخلايا و`source_ref` | معتمد كمثال سجل/حالة فقط | يفيد في immutable state transition، لكنه ليس نموذجاً فسيولوجياً مثبتاً ولا منفذاً للخوارزميات | محاكاة واختبارات |
| `uuid` و`float` في المحاكاة | لا يدخلان مسار النواة الحتمي | UUID عشوائي والعائمة والتقريب يضعفون إعادة الإنتاج ما لم يحدد البديل | محاكاة فقط |

## 3. بنية المقابض والموارد

### 3.1 قاعدة الملكية

كل مورد خارجي في UORI يمثل بمقبض typed لا برقم مجرد في الواجهات الداخلية. في المضيف يمكن أن يكون المقـبض `OwnedFd` عند الملكية و`BorrowedFd<'a>` عند الاستعارة. لا يُسمح بتخزين `BorrowedFd` بعد انتهاء العمر، ولا بتحويل `RawFd` إلى مالك إلا عبر عقد FFI واضح يثبت أن الجهة الحالية تملك المورد وأنه صالح للإغلاق.

```rust
#[cfg(unix)]
use std::os::fd::{AsFd, BorrowedFd, OwnedFd};

#[cfg(unix)]
pub struct HostedChannel {
    owner: OwnedFd,
}

#[cfg(unix)]
impl HostedChannel {
    pub fn borrowed(&self) -> BorrowedFd<'_> {
        self.owner.as_fd()
    }
}
```

هذا المثال خاص بالبيئة المستضافة. في bare-metal لا يوجد `std::fs::File` بالضرورة ولا معنى عام لـ file descriptor؛ لذلك يستخدم UORI نوعاً مجرداً مثل `CapabilityHandle` يحتوي على فهرس المورد، ونوعه، وحقوقه، ومرجع دليله، من دون أن يمنح الرقم صلاحية بذاته.

### 3.2 بوابة المقابض

لا يُقبل مقبض إلا إذا اجتاز: اكتشافاً للقراءة، وتحققاً من النوع، وإثبات الملكية أو التفويض، وتحديد عمليات القراءة والكتابة، وحدود الحجم والزمن، وسياسة الإلغاء. يتحول المقبض إلى فعل خارجي عبر `AuthorizationGate` ثم `Bridge`، ولا تُستدعى أي قيمة نصية مثل `source_ref`.

```text
اكتشاف المورد
  ↓
CapabilityHandle typed
  ↓
فحص الملكية والنطاق والحدود
  ├─ نقص الدليل → ABSTAIN/BLOCKED
  ↓
Borrowed access أو Owned transfer
  ↓
Bridge مع سجل وبصمة
```

## 4. إدارة الذاكرة في bare-metal

`#![no_std]` يعني أن الكود يعتمد على `core` ولا يحصل تلقائياً على runtime أو heap أو واجهات نظام التشغيل. يمكن استعمال `alloc` فقط بعد توفير مخصص عام صحيح وربطه بذاكرة افتراضية وذاكرة فيزيائية صالحتين. لذلك تكون مراحل الذاكرة كما يأتي:

| المرحلة | المخصص | السماح |
|---|---|---|
| الإقلاع المبكر | bump/arena ثابت | مؤقت، بلا تحرير فردي، وبحدود ثابتة |
| بعد اكتشاف الإطارات | frame allocator بــ bitmap أو free-list | صفحات 4 KiB بحسب target/بنية MMU المثبتة |
| heap النواة | slab أو allocator مختبر | بعد اختبار التزامن وIRQ وOOM |
| الموارد المؤقتة | arenas قابلة لإعادة الضبط | لا تُعاد أثناء وجود مراجع حية |
| التوسع | طلب إطارات جديد | لا يتم إلا عبر عقد MMU وWatchdog |

يجب أن تكون دالة `align_up` محمية من overflow، وأن تكون التهيئة مرة واحدة ومثبتة، وأن يتحقق `dealloc` من المؤشر والحجم والمحاذاة. كما يجب منع أخذ قفل قد يؤدي إلى deadlock داخل سياق مقاطعة، أو تصميم مخصص IRQ-safe بدليل مستقل.

المثال الذري الوارد عن bump allocator لا يُدمج كما هو. عدّاد عدد التخصيصات لا يكفي وحده لإثبات سلامة إعادة المؤشر، ولا يثبت أن المؤشر الذي يحرر يخص هذا المجال أو أن التهيئة اكتملت قبل الاستخدام. سيُستخدم المثال فقط كمرجع تعليمي لاختبار أولي محدود، مع `dealloc` عديم الأثر، أو مع arena عمرها أقصر من كل مراجعها.

## 5. سياسة الحساب العددي

تطبق النواة القواعد الدستورية بالترتيب التالي. يُستخدم الحتمي عندما يكون المجال مستوفياً وحد الخطأ مقبولاً ومثبتاً. ويُستخدم الفتري عندما تكون الحدود مضمونة. ويُستخدم الاحتمالي عندما يكون التوزيع مبنياً على بيانات كافية ومعايراً. أما الذكاء الاصطناعي التوليدي فيقترح فرضيات أو شروحاً فقط. وعند نقص الدليل تكون النتيجة `ABSTAIN`.

لذلك يكون المسار الافتراضي:

1. أعداد صحيحة ذات عرض ثابت مع فحص overflow.
2. fixed-point بصيغة Q محددة عندما تكون الدقة والمدى مثبتين.
3. interval arithmetic عندما تكون الحدود أهم من قيمة تقريبية وحيدة.
4. soft-float فقط لضرورة هدف موثقة، مع اختبار رموز الربط واختبارات الحدود.
5. العائمة القياسية في المحاكاة أو الطبقة المستضافة فقط، مع توثيق التقريب وعدم مساواتها بإثبات النواة.

لا يكفي إضافة `compiler_builtins` لإثبات أن `__addsf3` أو `__mulsf3` يعطيان السلوك المطلوب في كل ABI. يجب ربط نسخة هدف محددة، وفحص الرموز، وتشغيل اختبارات قيم خاصة، وNaN/Infinity إن كانت العائمة مسموحة، وحدود overflow، ثم حفظ سجل البيئة والبصمة.

## 6. الإغلاق والربط بين Rust وAssembly وCoq

تُقسم الواجهة إلى ثلاث طبقات. طبقة Rust الآمنة تصف العقد والحدود. طبقة FFI صغيرة تحتوي على `unsafe` في مواضع محددة، وتتحقق من المحاذاة والحجم والملكية قبل الاستدعاء. وطبقة Assembly تنفذ primitive محدوداً لا يعرف سجلات النواة الداخلية ولا يقرأ من عناوين غير موصوفة.

تمثيل closure أو `dyn Fn` ليس ABI عاماً صالحاً لتبادل النواة؛ فهو يعتمد على compiler وtarget، وقد يضيف مؤشرات بيانات وvtable وdrop shim. إذا احتاج UORI إلى callback، يستخدم جدولاً ثابتاً من معرفات عمليات مع دالة توقيع معلنة، أو بنية `extern "C"` تحتوي على context pointer مملوك بعقد واضح، لا closure مجهولاً يعبر حدود FFI.

أما Coq فيثبت الدوال الرياضية ونطاقات المدخلات والتحويلات المحددة. ولا يُعلن نجاح التنفيذ الفعلي إلا بعد ربط النظرية بالـ primitive المجمّع، وفحص ABI، واختبار runtime على target محدد. وبغياب هذه السلسلة يبقى الحكم `MODEL_VERIFIED` أو `LINK_BLOCKED`، لا `HARDWARE_VERIFIED`.

## 7. تحويل نموذج الخلية إلى نموذج نواتي عام

المفيد من نماذج الخلايا هو فكرة **الانتقال غير المتغير للحالة**، وسجل الجين/المرجع بوصفه قيمة نصية لا تُنفذ، ونسخ الحالة مع مرجع الأصل، ومسار الرسائل الصريحة. أما قيم ATP والضغط والمعادلات العشرية وأسماء العمليات الحيوية فتبقى محاكاة توضيحية ولا تُقدم بوصفها نموذجاً علمياً أو آلية تحكم حقيقية.

في UORI العام تستبدل الخلية بـ `NucleusState`، ويستبدل الجين بـ `AlgorithmDescriptor`، وتصبح الإشارة `CapabilityMessage`. يحوي الوصف معرّفاً ثابتاً، وإصداراً، ونطاقاً، ومدخلات ومخرجات، وحدود موارد، وبصمة SHA-256، ومرجع مصدر نصياً. نقل المصدر أو نسخه لا يساوي قبوله ولا تشغيله.

```text
NucleusState ثابت
  + AlgorithmDescriptor غير منفذ
  + CapabilityMessage موثق
  → تحقق النطاق والهوية
  → قرار دستوري
  → خطة تنفيذ معلنة أو ABSTAIN
  → سجل نتيجة وبصمة
```

## 8. الاختبارات الإلزامية قبل الدمج

| المعرّف | الاختبار | نتيجة القبول |
|---|---|---|
| FD-01 | استعارة `AsFd` ثم إسقاط المصدر | يمنع المترجم الاستعمال بعد انتهاء العمر |
| FD-02 | نقل `OwnedFd` ثم إسقاط المصدر | يوجد مالك واحد وإغلاق واحد فقط |
| FD-03 | تحويل `RawFd` غير صالح | يرفضه عقد FFI ولا ينشئ مالكاً كاذباً |
| MEM-01 | تخصيص ومحاذاة وحدود heap | لا overflow ولا كتابة خارج المجال |
| MEM-02 | OOM | نتيجة صريحة قابلة للسجل، بلا فساد حالة |
| MEM-03 | تحرير مزدوج أو مؤشر غريب | رفض أو panic محكوم في بيئة الاختبار |
| MEM-04 | منافسة النوى وIRQ | لا deadlock ولا reset أثناء مراجع حية |
| NUM-01 | fixed-point وQ-format | خطأ ضمن الحد المثبت لكل المجال |
| NUM-02 | interval | الحدود لا تنكسر في القيم الطرفية |
| ABI-01 | Rust/Assembly | تطابق calling convention والحجم والمحاذاة |
| ABI-02 | رموز soft-float | كل رمز مطلوب موجود ومربوط للهدف نفسه |
| SEC-01 | `source_ref` ضار | يبقى قيمة نصية ولا يستدعى ولا يُفسر |
| SEC-02 | رسالة بلا تفويض | `BLOCKED` مع سجل وبصمة |
| EVID-01 | إعادة التشغيل | نفس المدخلات والإصدار تنتج السجل نفسه في المسار الحتمي |

## 9. الخلاصة التنفيذية

يُدمج من المدخلات: نموذج الملكية والاستعارة، typed handles، الفصل بين المستضاف وbare-metal، allocator متعدد المراحل، fixed-point والفتري، وimmutable state transitions. ويُترك: استعمال `std::fs::File` داخل النواة، الاعتماد على أرقام RawFd داخلياً، allocator الذري الوارد للإنتاج، الع closures عبر ABI، العائمة غير المبرهنة، UUID العشوائي، وتنفيذ `source_ref`.

هذه القرارات توسع بنية UORI من دون ادعاء قدرة غير مثبتة. المرحلة التالية المناسبة هي إنشاء crate Rust صغير مستقل يختبر `CapabilityHandle` وواجهة الذاكرة و`source_ref` بمعزل عن العتاد، ثم نقل primitive واحد فقط إلى Assembly بعد تثبيت target وكتابة إثبات حدوده.
