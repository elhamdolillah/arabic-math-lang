# معمارية نواة UORI المتكيفة

**الحالة:** `PLANNED_ARCHITECTURE` — مواصفة قابلة للاختبار، وليست إثباتاً لتشغيل عالمي أو اندماج تلقائي مع كل عتاد.

## 1. الغرض

نواة UORI هي طبقة خوارزمية محمولة تُثبت على عتاد متاح ومصرح به. مهمتها الأولى ليست التحكم بالجهاز، بل تكوين وصف محدود وقابل للمراجعة لقدراته: نوع المعالج، الذاكرة المتاحة ضمن نطاق القراءة، المداخل، المخارج، قنوات الاتصال، وسياسات التفويض. لا تُحوّل النواة الوصف إلى فعل إلا بعد اجتياز عقد التفويض والحدود والرجوع الآمن.

## 2. الوحدات الأساسية

| الوحدة | المسؤولية | الوضع الافتراضي | شرط الانتقال |
|---|---|---|---|
| `HardwareProbe` | قراءة وصف العتاد والمداخل والمخارج | قراءة فقط | سلامة المصدر وحدود القراءة |
| `CapabilityModel` | تمثيل القدرات والقيود | بيانات موصوفة لا أوامر | اكتمال الحقول الجوهرية أو الامتناع |
| `HypothesisEngine` | اقتراح أهداف محتملة للعتاد | اقتراح غير ملزم | وسم كل نتيجة كفرضية |
| `AuthorizationGate` | فحص الهوية والصلاحية والنطاق والإلغاء | رفض افتراضي | عقد موقع أو قابل للتحقق |
| `ChannelSelector` | اختيار أقل قناة أثراً | لا اتصال | وجود قناة مصرّح بها |
| `Announcer` | إنتاج إعلان محدود قابل للتتبع | لا إعلان | نجاح التفويض ومنع الأسرار |
| `AdapterRuntime` | تشغيل موائم داخل عزل | متوقف | عقد مدخلات ومخرجات وموارد |
| `Watchdog` | مراقبة الحدود والسلوك والإيقاف | مراقبة | سجل قابل للمراجعة |
| `EvidenceLedger` | حفظ الأحداث والبصمات والحكم | كتابة محلية مضبوطة | صيغة سجل ثابتة |

## 3. دورة التنفيذ غير القابلة للتجاوز

تسير النواة في الرسم التالي دون تخطّي مرحلة:

```text
ابدأ
  ↓
اكتشاف للقراءة فقط
  ↓
وصف القدرات والقيود
  ↓
فرضية موسومة وغير ملزمة
  ↓
فحص الهوية والصلاحية والنطاق والإلغاء
  ├─ غير كافٍ → ABSTAIN/BLOCKED → سجل → توقف آمن
  ↓
اختيار قناة منخفضة الأثر
  ↓
إعلان محدود أو لا إعلان
  ↓
تشغيل موائم معزول بعقد موارد
  ↓
مراقبة وإيقاف قابل للرجوع
  ↓
سجل نتيجة وبصمة SHA-256
```

## 4. عقد العتاد

يمثل كل جهاز بسجل لا يمنح صلاحيات بذاته. الحد الأدنى المقترح هو: `device_id`، و`hardware_class`، وقائمة `inputs`، وقائمة `outputs`، و`channels`، و`read_limits`، و`write_capabilities`، و`owner_policy`، و`evidence_ref`. وجود مخرج رقمي أو قناة شبكة لا يعني السماح باستعماله. كما أن تخمين الهدف من شكل الجهاز يبقى فرضية تحتاج اختباراً معيارياً.

## 5. عقد الفعل الخارجي

كل فعل خارجي يجب أن يحدد الجهة المستفيدة، ونوع الفعل، والقناة، والمدخلات، والأثر المتوقع، والحد الزمني، وحد الموارد، وشروط الإلغاء، ومرجع التفويض، ومرجع الدليل. تشمل القنوات النص والصوت والصورة والرسالة الشبكية وتغيير خرج IoT من صفر إلى واحد. عند غياب حقل جوهري تكون النتيجة `ABSTAIN` أو `BLOCKED`.

## 6. التعاون بين الأنوية

يتكون UORI العالمي — بوصفه هدفاً معمارياً — من أنوية متعددة ذات هويات منفصلة وسجلات محلية. لا توجد ثقة ضمنية بين الأنوية؛ فكل رسالة تحتاج هوية المرسل، والوجهة، والرقم التسلسلي، والوقت أو نافذة الصلاحية، ونوع الطلب، والبصمة أو التوقيع، وسياسة إعادة المحاولة. فشل الشبكة يؤدي إلى توقف آمن ولا يُحوّل إلى نجاح.

## 7. قبول الخوارزميات والموائمات

لا تُقبل خوارزمية مستوردة من الإنترنت أو من نواة أخرى اعتماداً على اسمها أو فائدتها المعلنة. تمر عبر فحص المصدر، والبصمة، والتبعيات، والصلاحيات، والسلوك المحدد، والموارد، والعزل، وقابلية الإزالة. البحث الشبكي نفسه عملية بيانات غير موثوقة حتى تُتحقق المصادر وتُثبت البصمات وتُفحص الخوارزمية في بيئة معزولة. الذكاء التوليدي يمكن أن يقترح موائماً أو يشرح نتيجة، لكنه لا يمنح صلاحية ولا يقرر السلامة.

## 8. قواعد المحتوى والسياسة

التمييز بين البرمجية الخبيثة وسياسة المحتوى إلزامي. يمكن رفض برنامج بسبب سلوك ضار أو تجاوز للعزل وفق اختبار أمني. أما تصنيف لعبة أو تطبيق بأنه غير تعليمي أو مضيع للوقت فيحتاج سياسة مستخدم صريحة، ومقاييس معلنة، وآلية اعتراض، وسجلاً يشرح القرار. لا يجوز للنواة حذف أو تعطيل برنامج لمجرد حكم قيمي غير قابل للتدقيق.

## 9. قواعد الإثبات

| الادعاء | الدليل المطلوب | الحكم قبل الدليل |
|---|---|---|
| قراءة خصائص جهاز محدد | اختبار probe قابل للإعادة وسجل بيئة | مخطط قابل للاختبار |
| تحديد هدف الجهاز | مجموعة بيانات ومعيار تقييم | فرضية |
| إرسال إعلان | جهاز وقناة وتفويض وسجل نجاح | `ABSTAIN` |
| تغيير خرج IoT | جهاز فعلي وعقد أمان واختبار إلغاء | `BLOCKED` بلا الجهاز |
| قبول خوارزمية من الإنترنت | مصدر وبصمة وعزل واختبار سلوك | مرفوض افتراضياً |
| تعاون أنوية عبر الشبكة | اختبار هوية ورسائل وفشل شبكي | مخطط |
| طرد برمجية ضارة | مجموعة اختبارات معيارية ومحرك موثق | غير مثبت |

## 10. الاختبارات الأولية المطلوبة

يجب أن تبدأ الاختبارات باختبار اكتشاف قراءة فقط، ثم اختبار رفض مخرج بلا تفويض، ثم اختبار قبول عقد صحيح، ثم اختبار إلغاء أثناء التشغيل، ثم اختبار عزل موائم يتجاوز مورده، ثم اختبار رسالة موقعة بين نواتين، ثم اختبار انقطاع الشبكة، ثم اختبار ثبات سجل الأدلة. يسجل كل اختبار الأمر والبيئة ورمز الخروج والمخرج المنزوع من الزمن والبصمة، وتُحفظ الحالات `PASS` و`FAIL` و`ABSTAIN` و`BLOCKED` منفصلة.

## 11. طبقة Rust وBare-Metal

تفصل النواة بين المنطق المشترك وبيئة التشغيل المستضافة وهدف bare-metal. في المضيف تُستخدم `AsFd` و`BorrowedFd` للاستعارة المرتبطة بالعمر، و`OwnedFd` للملكية التي تُغلق عند الإسقاط، بينما لا تُستخدم أرقام `RawFd` في الواجهات الداخلية إلا عند حدود FFI موثقة. في bare-metal لا يُفترض وجود `std::fs::File` أو file descriptor؛ بل تستخدم النواة مقابض قدرات typed مرتبطة بالنوع والحقوق ومرجع الدليل.

تبدأ الذاكرة بمخصص bump/arena مؤقت للإقلاع، ثم مخصص إطارات، ثم slab أو مخصص ثابت الكتل بعد إثبات التزامن وIRQ وOOM. لا يعتمد UORI على المثال الذري للبump allocator بصورته التعليمية للإنتاج، ولا يعيد المؤشر العام عند بلوغ عداد التخصيصات صفراً دون إثبات سلامة جميع المراجع. ويكون fixed-point أو الحساب الفتري هو المسار الافتراضي؛ أما `compiler_builtins` وsoft-float فخياران مشروطان بالهدف واختبار الربط والحدود، لا دليلاً حسابياً بذاتهما.

لا تعبر closures أو `dyn Fn` حدود ABI النواة الخام؛ تستخدم النواة جداول عمليات ثابتة أو واجهات `extern "C"` بعقود ملكية صريحة. ويُسمح بنقل نموذج الخلية إلى محاكاة الانتقال غير المتغير للحالة وسجلات الرسائل، لكن `source_ref` يظل قيمة نصية غير منفذة. تفاصيل القرار والاختبارات في `docs/UORI_RUST_BARE_METAL_KERNEL_DESIGN_AR.md`.

## 12. الحالة الرسمية

هذه الوثيقة تثبت وجود مواصفة معمارية مكتوبة فقط. لا تثبت أن UORI يكتشف كل عتاد، أو يندمج معه، أو يبحث وينفذ خوارزميات الإنترنت، أو يطرد الفيروسات، أو يعمل عالمياً بلا مركز، أو يرفض الألعاب تلقائياً. جميع هذه العناصر أهداف تحتاج اختبارات مستقلة، وتظل خاضعة للقاعدة الدستورية الخامسة عند نقص الدليل.
