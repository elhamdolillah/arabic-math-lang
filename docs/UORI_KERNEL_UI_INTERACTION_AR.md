# واجهة نواة UORI ومسار التفاعل مع المستخدم

**الحالة:** `DESIGN_PROPOSAL` — مواصفة قابلة للتنفيذ والاختبار، وليست دليلاً على أن الاستدعاء العالمي للخوارزميات منفذ فعلياً.

## 1. الفكرة المركزية

واجهة النواة في UORI ليست مكتباً ثابتاً ولا تطبيقاً ذا شكل واحد. إنها **نقطة اتصال أولية** بين المستخدم والنواة، تتكيف لاحقاً مع خصائص الجهاز: شاشة كبيرة، هاتف، ساعة ذكية، طرفية نصية، صوت، جهاز طبي، أو عتاد بلا شاشة. الحد الأدنى المشترك هو مدخل آمن يستطيع المستخدم من خلاله تقديم سؤال أو هدف أو إشارة أو طلب مساعدة.

بعد الإدخال، لا تبدأ الواجهة بتنفيذ كود مجهول. بل تحول المدخل إلى طلب مهيكل، ثم تبحث عن الخوارزميات أو الموائمات المناسبة في مستودعات مسجلة، وتتحقق من الهوية والبصمة والرخصة والنطاق والصلاحيات، ثم تعرض للمستخدم ما يمكن استعماله وما بقي فرضية أو محجوباً. بعد ذلك تبدأ المحادثة بوصفها قناة متابعة بين المستخدم والنواة، مع بقاء كل فعل حساس خلف التفويض والمراقبة وسجل الدليل.

## 2. اللغة الأصلية لنواة UORI

تُكتب نواة UORI وعقودها الدلالية والأمنية الأصلية باللغة العربية الرياضية، لأنها اللغة المرجعية التي تُعرّف معنى الطلب، وهوية الخوارزمية، وشروط المجال، وحدود الخطأ، والتفويض، وسجل الدليل. وبذلك لا تكون العربية الرياضية مجرد لغة عرض في الواجهة، بل لغة المصدر التي تُبنى فيها النواة قبل ترجمتها أو توليدها إلى أهداف تنفيذ أخرى.

تُسمى اللغات الأخرى — مثل Rust وAssembly وC وWASM أو لغات موائمات التشاتبوت — لغات ربط أو أهداف توليد أو لغات تشغيل منخفضة المستوى، ولا تغيّر المرجع الدلالي الأصلي. يجب أن يحافظ كل تحويل على عقد قابل للمقارنة، وأن يسجل الإصدار والبصمة والهدف، وأن يفشل أو يمتنع إذا تعذر إثبات التكافؤ المطلوب. أما وصف العربية الرياضية بأنها «لغة العالم الموحدة» فهو **هدف معياري عالمي للمشروع** وليس حقيقة تشغيلية مكتملة ما لم يصدر معيار منشور وتثبت قابلية النقل والقبول المستقل.

```text
العربية الرياضية: المصدر والمرجع الدلالي
        ↓
التحليل والتحقق والملكية والحدود
        ↓
توليد Rust / Assembly / WASM / موائمات خارجية
        ↓
اختبار التكافؤ والبصمة
        ↓
تنفيذ مقبول أو ABSTAIN
```

## 3. الواجهة المشتركة للتشاتبوت العالمية

تُعرَّف واجهة UORI هنا بوصفها **طبقة واجهة مشتركة متعددة المزوّدين** للتشاتبوت وخدمات الحوار العالمية. المقصود ليس أن UORI يملك كل التشاتبوت أو يستبدلها، بل أن المستخدم يتعامل مع نقطة دخول موحدة، بينما تتولى النواة اختيار المزوّد أو مجموعة المزوّدين وفق طلب مهيكل وسياسة المستخدم وحالة الدليل والقدرات المتاحة.

تتكون الواجهة المشتركة من أربعة مستويات منفصلة. المستوى الأول هو `CommonConversationUI` الذي يوحد إدخال الرسائل وعرض النص والصوت والصورة وحالة الجلسة. المستوى الثاني هو `ProviderAdapter` الذي يحول عقد UORI المعياري إلى واجهة كل مزوّد ويعيد النتيجة إلى الصيغة المعيارية. المستوى الثالث هو `RouterAndPolicy` الذي يختار المزوّد أو يرفض الاختيار، مع مراعاة الخصوصية والكلفة والسرعة والقدرة والدليل. المستوى الرابع هو `EvidenceAndConsent` الذي يسجل المزوّد والإصدار والسياسة والموافقة والبصمة والنتيجة دون منح المزوّد صلاحيات نواة تلقائية.

```text
المستخدم
  ↓
واجهة UORI المشتركة
  ↓
طلب محادثة معياري + سياسة خصوصية + قيود المستخدم
  ↓
موجّه المزوّدين
  ├─ Chatbot Adapter A
  ├─ Chatbot Adapter B
  ├─ Chatbot Adapter C
  └─ الامتناع عند غياب الدليل أو التفويض
  ↓
توحيد النتيجة وعرض مصدرها وحدودها
  ↓
محادثة UORI وسجل الأدلة
```

لا تعني وحدة الواجهة وحدة الحقيقة أو وحدة الصلاحيات. قد تقدم عدة تشاتبوت إجابات مختلفة، ولذلك تعرض UORI هوية كل مزوّد، ووقت الاستجابة، وإصدار النموذج أو الخدمة إن توفر، ونوع النتيجة، وما إذا كانت الإجابة حتمية أو احتمالية أو اقتراحية أو غير قابلة للتحقق. ولا يُدمج ناتج مزوّد في نواة UORI أو يُستخدم للتحكم بعتاد إلا بعد المرور ببوابة مستقلة.

| المجال الموحد | العقد المشترك | الاختلاف الذي يبقى خاصاً بالمزوّد |
|---|---|---|
| الرسالة | نص أصلي، دور المرسل، رقم الجلسة، اللغة، الخصوصية | صيغة API وحدود طول السياق |
| النتيجة | محتوى، حالة الدليل، المزوّد، الإصدار، المرجع | شكل الاستدلال أو الأدوات الداخلية |
| الأدوات | اسم الأداة، نطاقها، المدخلات، التفويض، الإلغاء | طريقة الاستدعاء والتنفيذ لدى المزوّد |
| الذاكرة | موافقة المستخدم، مدة الاحتفاظ، نطاق الجلسة | نظام الذاكرة وسياسة التخزين الخاصة بالمزوّد |
| السلامة | `ALLOW` أو `REVIEW` أو `BLOCKED` أو `ABSTAIN` | آليات الحماية الداخلية للمزوّد |

يجب أن يكون كل `ProviderAdapter` قابلاً للإيقاف والاستبدال، وألا يحتوي على أسرار المستخدم في السجل العام. كما لا يجوز للمحوّل تنفيذ أوامر مستخرجة من إجابة التشاتبوت تلقائياً؛ فالنتيجة بيانات مقترحة إلى أن تعتمدها بوابة الخوارزميات والتفويض.

## 3. دورة التفاعل الأساسية

```text
نقطة الإدخال الأولية
        ↓
تطبيع لغوي سطحي وحفظ النص الأصلي
        ↓
استخراج الهدف والقيود دون ادعاء فهم غير مثبت
        ↓
تكوين طلب UORI مهيكل
        ↓
البحث في المستودعات المسجلة ومصادر الأدلة
        ↓
بوابة قبول الخوارزمية
(هوية + بصمة + رخصة + تبعيات + سلوك + موارد)
        ↓
اختيار خوارزمية أو الامتناع
        ├─ لا دليل كافٍ → ABSTAIN
        ├─ خطر أو صلاحية ناقصة → BLOCKED
        ↓
خطة تنفيذ معلنة للمستخدم
        ↓
بدء محادثة مرتبطة بالطلب
        ↓
إجابات ونتائج وسجل SHA-256
```

تُفصل مرحلة **الاكتشاف** عن مرحلة **القبول** وعن مرحلة **التنفيذ**. العثور على مستودع أو خوارزمية لا يعني الثقة بها، وقبول الوصف لا يعني منحها صلاحية تشغيل، وبدء المحادثة لا يعني أن النواة نفذت فعلاً إجراءً خارجياً.

## 3. طبقات واجهة النواة

| الطبقة | وظيفتها | ما لا يجوز لها فعله |
|---|---|---|
| `InputSurface` | استقبال نص أو صوت أو صورة أو إشارة جهاز | تنفيذ نص الإدخال ككود |
| `RequestNormalizer` | حفظ الأصل وإنتاج تمثيل مهيكل محدود | تغيير المعنى أو اختراع نية |
| `IntentAndConstraintModel` | تمثيل الهدف والقيود والموارد المطلوبة | تقديم الفرضية كحقيقة |
| `AlgorithmDiscovery` | البحث في السجلات والمصادر المصرح بها | اعتبار نتائج البحث موثوقة تلقائياً |
| `AdmissionGate` | فحص الهوية والبصمة والرخصة والتبعيات والسلوك | تجاوز الرفض أو التفويض |
| `PlanPresenter` | عرض الخوارزميات المرشحة وخطة الفعل والأثر | إخفاء المخاطر أو الصلاحيات المطلوبة |
| `ConversationSession` | إدارة الحوار والقرارات والنتائج | تحويل الحوار إلى صلاحية ضمنية |
| `ExecutionBridge` | تمرير فعل مصرح إلى موائم معزول | استدعاء `source_ref` أو كود مجهول |
| `EvidenceLedger` | تسجيل المدخلات والقرارات والنتائج والبصمات | تسجيل أسرار أو بيانات شخصية بلا سياسة |

## 4. صيغة الطلب الأولي

يمثل الإدخال الأولي داخلياً بسجل لا يخلط بين النص والنية والتنفيذ:

```text
UoriRequest {
    request_id: ثابت وقابل للتتبع,
    user_input: النص الأصلي كما استُقبل,
    input_channel: نص | صوت | صورة | جهاز,
    language: ar أو لغة معلومة,
    parsed_goal: هدف مهيكل أو UNKNOWN,
    constraints: قيود مهيكلة,
    requested_effect: لا_أثر | قراءة | اقتراح | فعل_خارجي,
    device_context: قدرات الجهاز وحدوده,
    privacy_class: عام | شخصي | سري,
    evidence_ref: مرجع السجل,
    decision: DISCOVER | ABSTAIN | BLOCKED
}
```

يبقى `user_input` محفوظاً كما ورد، ويكون `parsed_goal` تمثيلاً قابلاً للمراجعة. إذا تعارض النص الأصلي مع التحليل أو تعذر تحديد المقصود، لا تُخمن النواة؛ بل تطلب توضيحاً أو تعلن `ABSTAIN`.

## 5. استدعاء الخوارزميات من المستودعات

تبحث `AlgorithmDiscovery` في سجل خوارزميات معروف، أو في مصادر يسمح بها المستخدم أو سياسة المؤسسة. لكل نتيجة يجب أن تتوفر هوية خوارزمية وإصدار وبصمة SHA-256 ومصدر ورخصة وتبعيات ونطاق مدخلات ومخرجات وحدود موارد وحالة تحقق. لا يكفي اسم المستودع أو عدد النجوم أو وصف مولد آلياً.

يمر المرشح بالمراحل الآتية:

| المرحلة | الحكم الممكن |
|---|---|
| العثور على المصدر | `FOUND`، ولا يعني القبول |
| مطابقة الهوية والبصمة | `IDENTIFIED` أو `UNVERIFIED` |
| فحص الرخصة والملكية | `ADMISSIBLE` أو `LICENSE_BLOCKED` |
| تحليل التبعيات والسلوك | `REVIEW_REQUIRED` أو `BEHAVIOR_BLOCKED` |
| اختبار الموارد والعزل | `SANDBOX_READY` أو `ISOLATION_BLOCKED` |
| توافق الهدف والبيانات | `COMPATIBLE` أو `ABSTAIN` |
| منح صلاحية التنفيذ | لا يتم إلا بعقد تفويض مستقل |

الذكاء الاصطناعي التوليدي يجوز أن يقترح خوارزميات أو يشرح فروقها، لكنه لا يمنحها هوية ولا يثبت سلامتها ولا يتجاوز بوابة القبول.

## 6. مسار طلب المستخدم إلى الكود والتنفيذ

يكتب المستخدم طلبه في واجهة UORI، ثم تحول النواة الطلب إلى مواصفة مهيكلة تتضمن الهدف والمدخلات والمخرجات والقيود ونطاق التأثير. تستعمل طبقة LLM للبحث عن كود أو خوارزمية مناسبة، أو لتوليد اقتراح أولي عند غياب كود موثق. ويظل ما يعيده LLM **مرشحاً غير موثوق** إلى أن يمر ببوابة الهوية والفحص والاختبار.

```text
طلب المستخدم
  ↓
تحليل الهدف والقيود
  ↓
LLM: بحث عن كود موثق أو اقتراح كود
  ↓
تصنيف المرشح
  ├─ حتمي موثق ومجاله مستوفٍ وحد الخطأ مقبول
  ├─ فتري بحدود مضمونة
  ├─ احتمالي ببيانات كافية ومعايرة
  └─ غير مثبت → ABSTAIN
  ↓
ترتيب الأولوية
  حتمي ← فتري ← احتمالي
  ↓
فحص الهوية والبصمة والرخصة والتبعيات
  ↓
تحليل ساكن واختبارات وحدود وموارد وعزل
  ↓
خطة تنفيذ قابلة للمراجعة
  ↓
تفويض صريح عند وجود أثر خارجي
  ↓
تنفيذ مراقب أو امتناع
```

### قاعدة أولوية الكود

إذا كان هناك كود حتمي صالح للمجال، موثق الهوية والبصمة، ومثبت حد الخطأ ومنع الفيض والتدفق غير المسموح، فهو الخيار الأول. ويُستخدم الكود الفتري عندما تكون الحدود مضمونة حتى إن لم تكن النتيجة قيمة مفردة. ولا يُستخدم الكود الاحتمالي إلا إذا كان التوزيع مبنياً على بيانات كافية ومعايراً، مع عرض عدم اليقين ومصدر البيانات. لا يجوز اختيار كود احتمالي لمجرد أنه أسرع أو أكثر إقناعاً لغوياً إذا كان البديل الحتمي أو الفتري مستوفياً.

هذه القاعدة ترتيب قرار إجرائي، وليست دليلاً على أن الكود الحتمي صحيح في كل مسألة. تفحص النواة الفئات بالترتيب `DETERMINISTIC` ثم `INTERVAL` ثم `PROBABILISTIC`، وتقبل أول مرشح مستوفٍ. ولا تنتقل إلى فئة أدنى إلا بعد تسجيل سبب رفض المرشحين في الفئة الأعلى. يحظر `fallback` الاحتمالي الصامت، ولا يرفع إقناع LLM أو سرعته تصنيف المرشح. يجب أن يكون المجال مستوفياً، وأن تكون المدخلات ضمن الحدود، وأن تكون حالات الفشل والفيض ومعالجة الموارد معرفة. عند تعارض نتائج مرشحين أو نقص الدليل، تكون النتيجة `ABSTAIN` أو `REVIEW_REQUIRED` بدلاً من المزج الصامت بين كود حتمي واحتمالي.

### فصل الجلب عن التنفيذ

لا يجوز للنواة تشغيل النص البرمجي الذي جلبه LLM مباشرة، ولا تنفيذ أوامر موجودة في مستودع لمجرد أن المزوّد رشحها. يُحفظ الكود المرشح مع مصدره وإصداره وبصمته، ثم يمر بفحص ساكن واختبارات داخل بيئة معزولة وحدود زمنية وذاكرة وملفات وشبكة. بعد ذلك فقط يمكن إنشاء عقد تنفيذ يحدد المدخلات والمخرجات والصلاحيات وشروط الإيقاف. أفعال العتاد أو الشبكة أو البيانات الشخصية تحتاج تفويضاً مستقلاً، أما الفشل في الفحص فيقود إلى `BLOCKED` أو `ABSTAIN`.

| مخرج LLM | وضعه في UORI | القرار الافتراضي |
|---|---|---|
| رابط أو كود حتمي موثق | مرشح قابل للفحص | لا تنفيذ قبل التحقق |
| كود فتري بحدود مثبتة | مرشح مقبول مشروطاً | اختبار الحدود ثم التفويض |
| كود احتمالي معاير | مرشح بحثي أو تنبؤي | لا يتحول إلى حقيقة حتمية |
| كود مولد بلا مصدر أو برهان | فرضية تنفيذية غير مثبتة | `ABSTAIN` |
| أمر ذو أثر خارجي | فعل حساس | تأكيد وتفويض وعزل وسجل |

## 7. بدء المحادثة

تبدأ المحادثة بعد تكوين نتيجة أولية، لا بعد تنفيذ صامت. تعرض الواجهة للمستخدم ملخصاً يتضمن: ما فهمته النواة من الطلب، وما الخوارزميات المرشحة، ودرجة حالة الدليل، وما البيانات التي ستُستخدم، وما الأثر المتوقع، وما الصلاحية المطلوبة، وما الذي لم تستطع النواة إثباته.

ثم تتحول الجلسة إلى حالات محددة:

```text
NEW
  → CLARIFICATION_REQUIRED
  → DISCOVERY_COMPLETE
  → ADMISSION_REVIEW
  → PLAN_READY
  → USER_CONFIRMATION_REQUIRED
  → RUNNING
  → RESULT_WITH_EVIDENCE
  → CLOSED أو ABORTED
```

لا تُفسر مواصلة المستخدم للمحادثة على أنها موافقة على فعل خارجي. الأفعال التي تغير جهازاً أو تتصل بنواة أخرى أو تنشر بيانات تحتاج تأكيداً صريحاً، وتفويضاً صالحاً، وشروط إلغاء.

## 7. التكيف مع الجهاز

تقدم النواة النموذج المنطقي نفسه على كل جهاز، لكن `PresentationAdapter` يختار الشكل المناسب من قدرات الجهاز والمستخدم. فقد يصبح المدخل مربعاً نصياً في الحاسوب، أو زرّاً وصوتاً في الساعة، أو واجهة لمس، أو قناة صوتية، أو بروتوكولاً آلياً لجهاز بلا شاشة. هذا التكيف يغير طريقة العرض ولا يغير قواعد الأمان أو مراحل القبول.

إذا أظهرت `HardwareProbe` أن الجهاز لا يملك قناة إخراج مناسبة، تعرض النواة النتيجة محلياً أو تسجلها فقط. وجود Bluetooth أو USB أو شبكة لا يمنح الإرسال تلقائياً؛ فالقناة تحتاج تفويضاً ونطاقاً وسياسة خصوصية.

## 8. الخصوصية والأدلة

يُصنف الإدخال قبل إرساله إلى أي مستودع أو نواة أخرى. البيانات العامة العلمية يمكن تمريرها وفق الرخصة، أما البيانات الشخصية أو السرية فلا تُرسل إلا بقاعدة صريحة وموافقة مناسبة. يحفظ سجل الأدلة مراجع وبصمات وقرارات، لا محتوى سرياً غير ضروري.

يجب أن يستطيع المستخدم التمييز بين أربع نتائج: **إجابة حتمية** ضمن مجال مثبت، و**إجابة فترية** بحدود مضمونة، و**اقتراح احتمالي** مبني على بيانات ومعايرة، و**امتناع** بسبب نقص الدليل. كما يجب أن يميز بين اقتراح خوارزمية وبين تنفيذها فعلاً.

## 9. واجهة محادثة عربية أولاً

تكون العربية الرياضية المرجع الدلالي الأول لحقول الطلب والنتيجة. ويمكن قبول لغات أخرى عبر طبقة ترجمة، لكن النص العربي أو التمثيل الرياضي المعياري يبقى قابلاً للمراجعة. لا تُخفى المصطلحات التقنية؛ بل تعرض الواجهة الاسم العربي، والهوية المعيارية، والإصدار، وحالة الدليل، والصلاحية المطلوبة.

مثال عرض أولي:

```text
الطلب: أريد معرفة هل يستطيع هذا الجهاز إرسال قراءة إلى نواة أخرى.

ما ثبت: وجود قناة اتصال موصوفة قراءةً.
ما لم يثبت: صلاحية الإرسال، هوية الطرف الآخر، وسلامة البيانات.
المرشحون: موائم الاتصال X، الإصدار 2، البصمة ...
القرار الحالي: ABSTAIN قبل التفويض والاختبار.
السؤال التالي: هل تسمح بإنشاء خطة فحص قراءة فقط؟
```

## 10. الحدود الحالية

هذه الوثيقة تثبت مساراً معمارياً لواجهة النواة، ولا تثبت وجود محرك بحث عالمي أو قبولاً آلياً للخوارزميات أو محادثة موزعة مكتملة. يلزم قبل إعلان التنفيذ إنشاء نموذج أولي محلي يختبر دورة `Input → Request → Discovery → Admission → Conversation` باستخدام سجل ثابت، ومصادر اختبار محلية، وخوارزميات وهمية غير قابلة للتنفيذ، ثم إضافة مصدر خارجي واحد في بيئة معزولة بعد فحصه.

**النتيجة المعتمدة:** واجهة UORI هي بوابة حوار واكتشاف وتفويض، وليست منفذاً مباشراً لكل ما يكتبه المستخدم أو لكل خوارزمية يعثر عليها البحث. الحوار هو الطبقة التي تشرح وتطلب التوضيح وتعرض الدليل؛ أما التنفيذ فلا يبدأ إلا بعد المرور بالعقود الدستورية والأمنية.
